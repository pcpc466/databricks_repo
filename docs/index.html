01The Problem

Sales data lived in two disconnected systems. The CRM held customers, products and sales transactions; the ERP held customer demographics, locations and the product category hierarchy. Neither was clean: whitespace-padded strings, coded values like M/S, dates stored as yyyyMMdd integers (some zero or malformed), missing or negative prices, and customer IDs formatted differently in each system.

The goal was a single, trusted star schema — one sales fact table and two conformed dimensions — that BI tools can query directly, rebuilt automatically from the raw files in one run.

03Data Ingestion — Bronze

Raw CSV exports are uploaded to a Unity Catalog Volume, which gives governed file storage without managing mount points or storage keys. The bronze notebook reads each file with header detection and schema inference, then lands it unchanged as a managed Delta table. Keeping bronze untouched means any downstream bug can be fixed and replayed without re-pulling source data.

PySpark · Bronze_layer
df = (spark.read
        .option("header", "true")
        .option("inferSchema", "true")
        .csv("/Volumes/databricksprash/bronze_layer_data/source_system/source_crm/cust_info.csv"))

df.write.mode("overwrite").saveAsTable("bronze_layer_data.crm_cust_info")

The same read → write pattern runs for all six sources. Writes use overwrite, so every run is a clean, idempotent full refresh.

04Transformation & Cleaning — Silver

Each source gets its own silver notebook so cleaning rules stay small, readable and testable. Every notebook follows the same structure: read bronze → trim → fix → rename → sanity check → write Delta.

Reusable step: trim every string column

Instead of naming columns one by one, the notebook walks the DataFrame schema and trims whatever is a string — so it keeps working if the source adds columns.

PySpark · all silver notebooks
for field in df.schema.fields:
    if isinstance(field.dataType, StringType):
        df = df.withColumn(field.name, trim(col(field.name)))

Decoding cryptic codes into readable values

CRM stores marital status and gender as single letters in inconsistent case. These are normalized to full words; unknown values pass through untouched instead of being guessed.

PySpark · Silver_layer_crm_cust_info
df = (df
  .withColumn("cst_marital_status",
      F.when(F.upper(F.col("cst_marital_status")) == "S", "Single")
       .when(F.upper(F.col("cst_marital_status")) == "M", "Married")
       .otherwise(F.col("cst_marital_status")))
  .withColumn("cst_gndr",
      F.when(F.upper(F.col("cst_gndr")) == "M", "Male")
       .when(F.upper(F.col("cst_gndr")) == "F", "Female")
       .otherwise(F.col("cst_gndr"))))

df = df.filter(col("cst_id").isNotNull())   # drop rows with no customer ID

Parsing a composite product key

The CRM product key packs the category and product number into one string (e.g. CO-RF-FR-R92B-58). Splitting it creates a cat_id that matches the ERP category table — the join key that didn't exist before.

PySpark · Silver_layer_crm_prd_info
# first 5 chars → category id, reformatted to match ERP ("CO-RF" → "CO_RF")
df = df.withColumn("cat_id", F.regexp_replace(F.substring(col("prd_key"), 1, 5), "-", "_"))
# the rest → product number used by the sales table
df = df.withColumn("prd_key", F.substring(col("prd_key"), 7, F.length(col("prd_key"))))

df = df.withColumn("prd_cost", F.coalesce(col("prd_cost"), F.lit(0)))   # missing cost → 0

Repairing integer dates

Sales dates arrive as integers like 20101229. Zeros and values that aren't exactly 8 digits are invalid, so they become NULL rather than producing nonsense dates; the rest are parsed into real DATE values.

PySpark · Silver_layer_sales_details
df = df.withColumn("sls_order_dt",
    F.when((col("sls_order_dt") == 0) | (length(col("sls_order_dt")) != 8), None)
     .otherwise(F.to_date(col("sls_order_dt").cast("string"), "yyyyMMdd")))
# same rule applied to sls_ship_dt and sls_due_dt

Deriving missing or invalid prices

When a price is null or non-positive, it is recomputed from sales ÷ quantity, with a guard against dividing by zero.

PySpark · Silver_layer_sales_details
df = df.withColumn("sls_price",
    F.when(col("sls_price").isNull() | (col("sls_price") <= 0),
        F.when(col("sls_quantity") != 0, col("sls_sales") / col("sls_quantity"))
         .otherwise(None))
     .otherwise(col("sls_price")))

Making ERP keys match CRM keys

The ERP systems format customer IDs differently (a NAS prefix in one table, dashes in another). Standardizing them is what lets the gold layer join CRM and ERP at all. Future birthdates are nulled and country codes are expanded.

PySpark · Silver_erp_cust / Silver_erp_loc
# "NASAW00011000" → "AW00011000"
df = df.withColumn("cid",
    F.when(col("cid").startswith("NAS"), F.substring(col("cid"), 4, F.length(col("cid"))))
     .otherwise(col("cid")))

df = df.withColumn("bdate", F.when(col("bdate") > F.current_date(), None).otherwise(col("bdate")))

# location table: "AW-00011000" → "AW00011000", country codes → names
df = df.withColumn("cid", F.regexp_replace(col("cid"), "-", ""))
df = df.withColumn("cntry",
    F.when(col("cntry") == "DE", "Germany")
     .when(col("cntry").isin("US", "USA"), "United States")
     .when((col("cntry") == "") | col("cntry").isNull(), "n/a")
     .otherwise(col("cntry")))

Business-friendly column names

A rename map per table turns source abbreviations into names analysts can read without a data dictionary.

PySpark · Silver_layer_sales_details
RENAME_MAP = {
    "sls_ord_num": "order_number",  "sls_prd_key": "product_number",
    "sls_cust_id": "customer_id",   "sls_order_dt": "order_date",
    "sls_sales":   "sales_amount",  "sls_quantity": "quantity",  "sls_price": "price",
}
for old, new in RENAME_MAP.items():
    df = df.withColumnRenamed(old, new)

df.write.mode("overwrite").format("delta").saveAsTable("silver_layer_data.crm_sales")

05Gold Table Conversion — Star Schema

The gold layer is written in Spark SQL because it's mostly joins. It merges CRM and ERP into conformed dimensions, assigns surrogate keys with ROW_NUMBER(), and builds a fact table that references dimensions by those keys rather than by source-system IDs.

dim_customers — merging two systems' view of a customer

CRM is treated as the source of truth for gender; ERP fills the gap only when CRM says n/a. Country and birthdate come from ERP.

Spark SQL · gold_dim_customers
SELECT
  ROW_NUMBER() OVER (ORDER BY ci.customer_id) AS customer_key,   -- surrogate key
  ci.customer_id, ci.customer_number, ci.first_name, ci.last_name,
  lo.country,
  ci.marital_status,
  CASE WHEN ci.gender <> 'n/a' THEN ci.gender            -- CRM is master
       ELSE COALESCE(ca.gender, 'n/a') END AS gender,      -- ERP as fallback
  ca.birth_date AS birthdate,
  ci.created_date AS create_date
FROM silver_layer_data.customer_info ci
LEFT JOIN silver_layer_data.erp_customers ca         ON ci.customer_number = ca.customer_number
LEFT JOIN silver_layer_data.erp_customer_location lo ON ci.customer_number = lo.customer_number

dim_products — current products with their category hierarchy

Only active products (no end date) are kept, enriched with category, subcategory and maintenance flag from ERP.

Spark SQL · gold_dim_products
SELECT
  ROW_NUMBER() OVER (ORDER BY cp.start_date, cp.product_number) AS product_key,
  cp.product_id, cp.product_number, cp.product_name,
  cp.category_id, cat.category, cat.subcategory, cat.maintenance_flag,
  cp.product_line, cp.start_date
FROM silver_layer_data.crm_products cp
LEFT JOIN silver_layer_data.erp_product_category cat ON cp.category_id = cat.category_id
WHERE cp.end_date IS NULL   -- drop historical product versions

fact_sales — transactions keyed to the dimensions

Spark SQL · gold_fact_sales
SELECT
  cs.order_number, pr.product_key, cu.customer_key,
  cs.order_date, cs.ship_date, cs.due_date,
  cs.sales_amount, cs.quantity, cs.price
FROM silver_layer_data.crm_sales cs
LEFT JOIN gold_layer_data.dim_products  pr ON cs.product_number = pr.product_number
LEFT JOIN gold_layer_data.dim_customers cu ON cs.customer_id    = cu.customer_id
PySpark · write to gold

06Orchestration

The pipeline runs as one Databricks Job, Pipelines_running, with three dependent tasks. Each layer only starts when the previous one succeeds, so gold is never built on half-refreshed silver data.

bronze_layeringest 6 CSVs
→
silver_layer6 cleaning notebooks
→
gold_layer2 dims → 1 fact

Inside a layer, a small orchestration notebook fans out to the per-table notebooks with dbutils.notebook.run. A failure is logged per notebook rather than silently swallowed, which makes the job's run output easy to debug.

PySpark · silver_orchestration
notebooks = [
    "./crm/Silver_layer_crm_cust_info", "./crm/Silver_layer_crm_prd_info",
    "./crm/Silver_layer_sales_details", "./erp/Silver_erp_cust",
    "./erp/Silver_erp_loc",             "./erp/Silver_erp_px_car",
]
for nb in notebooks:
    print(f"Running {nb}")
    try:
        dbutils.notebook.run(nb, timeout_seconds=3600)
        print(f"Finished {nb}")
    except Exception as e:
        print(f"Failed to execute {nb}: {e}")

Gold runs its notebooks in a fixed order — dimensions first, then the fact table, because the fact table looks up the dimensions' surrogate keys.

PySpark · gold_orchestration
for nb in ["./gold_dim_customers", "./gold_dim_products", "./gold_fact_sales"]:
    print(f"Running {nb}")
    dbutils.notebook.run(nb, timeout_seconds=0)

All code lives in a Databricks Git folder synced to GitHub, so every change to a cleaning rule is versioned and reviewable.

07Key Takeaways

  • Keep bronze raw. Because nothing is cleaned on ingest, fixing a silver rule only means re-running from bronze — never re-sourcing data.
  • Key alignment is the real integration work. The joins in gold only work because silver standardized ERP and CRM IDs and split the composite product key.
  • Surrogate keys decouple analytics from source systems. The fact table doesn't care how CRM or ERP format their IDs.
  • Order matters in orchestration. Task dependencies (layer to layer) and notebook order (dims before fact) keep every run consistent.

Next steps

Switch full overwrites to incremental MERGE INTO loads, add automated data-quality checks (row counts, null and key-integrity tests) as a job task, and schedule the job to run on a trigger when new files land in the Volume.
